# 需求协议提案（Requirements Protocol Proposal）

> 状态：**提案**——供设计独立需求协议使用。本文是从 Anchorlaw v0.11 裁剪出的需求发掘阶段的设计提案；需求协议与 Anchorlaw（编程执行协议）、RE 框架（逆向探索协议）三者闭环覆盖完整业务逻辑。

## 1. 背景与动机

Anchorlaw v0.10 曾把「需求发掘」纳入 Judge 驱动的六段执行流水线。实践与结构分析发现这是**结构反转**：

1. **驱动方式错位**：编程是构建型工作（判据驱动收敛），需求发掘是**探索型**工作（探索人类的意图）——探索型应由 Scout 驱动，Judge 只做技术审核，而不是反过来的「Judge 驱动 + Scout 当分析工具」。
2. **人机对话本质**：需求发掘的核心是**与需求方（人类）的对话**——澄清、提问、往返确认。而 subagent 的 Scout 是隔离进程，**无法直接与人沟通**，只能单向分析主会话转交的输入。让「无法对话的 Scout」去做「本质是对话的需求发掘」必然失败。
3. **结论**：需求发掘必须从执行拓扑摘出，成为**独立的协议**——由能与人对话的执行者（主会话扮演 Scout）驱动，Judge 独立做技术审核，产出确认后的需求与规范，交给 Anchorlaw 执行。

## 2. 三协议闭环

| 协议 | 职责 | 驱动方式 | 输入 → 输出 |
|------|------|----------|-------------|
| **需求协议**（本提案） | 发掘完整需求、确定技术约束规范 | Scout 驱动（人机对话）+ Judge 技术审核 | 模糊意图 → 已确认需求文档 + 技术约束规范 |
| **Anchorlaw**（v0.11） | 编程实施 + 验证 | Judge 驱动（四段流水线） | 已确认需求/规范 → 实现 + 验证证据 |
| **RE 框架**（如 CoreSwap） | 逆向探索 | 探索驱动（scan → 发现 → 收敛） | 目标程序 → 逆向结论 + 确定的编程任务（调用 Anchorlaw 实施） |

三者闭合：**需求协议**把未知意图变成确定需求 → **Anchorlaw** 把确定需求变成代码 → **RE 框架**在逆向中发现确定需求（实现需求天然确定），直接调用 Anchorlaw 实施。

## 3. 核心模型：Scout 驱动 + Judge 技术审核

```
人类（需求方） ⇄ Scout（主会话扮演，探索驱动） → 需求文档/规范草案
                                            ↓（交审）
                                        Judge（技术审核：可实现性 / 判据可验证性）
                                            ↓（通过）
                                    已确认需求文档 + 技术约束规范
```

### 3.1 Scout —— 需求对话的驱动者

- **形态**：主会话扮演的**探索角色**（inline）——因为只有主会话能直接与人对话；subagent 无法与人沟通是本协议成立的先决原因。
- **职责**：
  - 向需求方提问、澄清歧义、挖掘隐含约束；
  - 把需求整理成**声称**（可验证的 → 将来绑 `@anchor.test`）与**边界**（不可验证/超出范围的 → `@anchor.idk`）；
  - 记录**技术约束**（平台/语言、外部依赖、性能目标、客户强制的架构决策）——架构设计（模块划分/依赖方向/接口）属 Anchorlaw stage-1 产出，不在需求侧设计。
- **探索模式**：一次提问 → 回答 → 澄清 → 再提问，直到需求收敛。

### 3.2 Judge —— 技术审核者（独立）

- **形态**：隔离 subagent（或独立审核视角）——需求是 Scout 驱动的产物，Judge 审核必须独立（自评≠审查，与 Anchorlaw §15.4 同原则）。
- **职责**：审核需求文档的
  1. **可实现性**——依赖、平台、数据前提是否满足；
  2. **判据可验证性**——需求中的声称能否绑定可执行验证；
  3. **完整性**——歧义/矛盾/缺失是否已澄清。
- **不驱动**：Judge 只审不发问，对话由 Scout 驱动。

### 3.3 人类 —— 需求方 + 最终拍板

- 需求确认（人类点头「需求清楚、可以实施」）→ 产出进入 Anchorlaw 输入契约。

## 4. 产出契约（供 Anchorlaw 消费）

需求协议交付：**已确认需求文档 + 技术约束规范**（架构设计由 Anchorlaw stage-1 产出），构成 Anchorlaw 的 stage-0 输入契约（协议 §15.1）：

```
Input contract:
- 需求文档（confirmed）：功能声称列表 + 边界声明（@anchor.idk 语义）
- 技术约束规范：平台/语言、外部依赖、性能目标、客户强制的架构决策（架构设计由 Anchorlaw stage-1 产出）
```

Anchorlaw 的 Judge 从该输入推导**验收判据**（声称 + 验证载体 + 边界）后开始实施——不再重新发掘需求。

## 5. 与 Anchorlaw 的交接（§16.1 语义）

- 需求协议的人类确认 = Anchorlaw 的实施授权（host handover）；
- Anchorlaw 内 confirm hook 单节点化（交付 `confirmed` 授予）；
- 交接失败（需求不完整/不可实现）→ 退回需求协议继续 Scout 对话，不进 Anchorlaw。

## 6. 设计要点（避免重蹈 v0.10 覆辙）

1. **对话必须是第一公民**：需求协议的每个环节都要有人类可参与的往返；任何「无法与人沟通的执行者」都不适合做需求驱动。
2. **探索与构建分离**：探索型工作（需求/逆向）与构建型工作（编程实施）用不同驱动方式；不要用判据驱动的流水线套探索型工作。
3. **审核独立**：产出方（Scout/主会话）与审核方（Judge）分离，守住自评≠审查。
4. **产出即契约**：协议边界 = 产出文档（需求 + 规范 + 判据），下游协议只消费产出，不重新发掘。
